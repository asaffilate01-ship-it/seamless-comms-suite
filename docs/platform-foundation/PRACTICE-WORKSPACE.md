# CRM & Practice workspace

This feature extends the existing `crm.core` and `practice.core` modules on the platform engines foundation. It does not create another client database or automatically activate subscriptions.

## Implemented

- `/app/crm`: people, companies, leads and tasks with create/edit forms, company/contact associations and activity timelines. Existing opportunities are visible; the sales pipeline editor remains separate work.
- `/app/practice`: Today, searchable work board/table, client workspaces, versioned service templates, proposals, time/cost reporting and industry packs.
- `/client-portal`: explicit client memberships; only the client's jobs, requests and issued proposals are returned. Internal deadlines, staff costs and template budgets are not exposed.
- Templates for accounting, compliance, legal intake, venue onboarding, creative production, supplier onboarding and childminder applications. Industry packs are operational templates, not regulatory determinations.
- Practice clients can link to an existing CRM company; server checks reject cross-tenant links.
- Atomic job creation and phase instantiation; unique client/template/period prevents duplicates. Template snapshots preserve historical jobs and quotes.
- Internal targets and external deadlines remain separate. Phase order, outstanding requests and optimistic revisions are enforced in the database. Legacy direct engagement writes cannot bypass gates on template-managed jobs.
- Pricing: integer minor-unit base price + units × unit price + catch-up fee, with a snapshot of terms and price. This is not an arbitrary formula evaluator or tax engine.
- Portal publication and authenticated client-owner acceptance/decline, with immutable proposal snapshots and audit entries. This is **not** provider-backed e-signature or payment collection.
- Client factual responses and staff acceptance/re-request; file exchange in a private Supabase Storage bucket. PDF/PNG/JPEG/CSV, 5 MB maximum, SHA-256, short-lived download URLs and access rechecks. Uploads are not automatically marked accepted.
- Recorded time, phase budgets and cost calculations in each job's currency. Costs and quoted fees are not presented as recognised revenue/profit.
- Optional recurring schedules per client/template, pause/resume and anchored month-end dates. The worker creates jobs once per period, with explicit configured deadline offsets. It does not infer statutory dates.
- Opt-in reminder events: at most three, three days apart, only for outstanding overdue requests. Responses and closed jobs stop subsequent events. These are events, not proof of delivery.
- `practice.core` is available as an optional module to platform/landlord/standalone/variant products. Existing defaults remain intact. No invented add-on prices and no tenant enablement during migration.

## Database and security

Apply the foundation migrations before:

1. `20260930210000_omniqora_practice_workspace.sql`
2. `20260930211000_omniqora_practice_automation.sql`

Staff mutations use authenticated database RPCs. Every operation checks active tenant product, unexpired Practice entitlement and tenant role. Template and automation configuration require owner/admin; agents can deliver work. New table writes are not granted directly to authenticated callers. Portal requests require a matching active client membership, and only `client_owner` can accept proposals. `client_viewer` has no write access.

Private files use `practice-request-files`. The server lazily provisions this bucket as private with MIME and size limits; a public bucket is rejected. No anonymous storage policies are installed. Storage paths are generated by the server. The existing Supabase server credential is required for private upload/download operations. File signature checks are included; dedicated malware scanning/quarantine is not yet integrated.

## Deployment / activation

- This change is reviewed against the active platform foundation branch, not deployed to production.
- Apply migrations in staging, enable `practice.core` and dependencies for a test tenant product, then exercise both a staff account and a client account.
- Portal users must already have accounts. Staff can grant client access; no invitations/emails are sent by this flow.
- Configure an external scheduler to POST `{ "limit": 50 }` to `/api/platform/workers/practice` with the existing `OMNIQORA_WORKER_TOKEN` (at least 32 characters). Start with a daily schedule. No scheduler is installed or activated by this PR.
- Recurring schedules use date-only period anchors and noon UTC for explicit deadline offsets. Catch-up is bounded to one occurrence per due schedule per invocation.
- Reminder events use `practice.request.reminder_due`. Connect/automation delivery must be configured independently, with channel permission, recipient resolution, and a final outstanding-request check before sending. No generic delivery binding is enabled here.
- External signatures, invoices/payments and statutory submissions continue to require their provider integrations. Client acceptance must not be shown as provider signature completion.
- No other SaaS repository or live tenant is migrated by this PR. Each product opts in through the existing catalogue, provisioning and entitlement flow.

## Remaining scope for full Engager-style parity

Provider-backed e-signature, outbound delivery binding, branded portal domains/themes, visual conditional workflow builder, custom form builder, calendar view, proposal PDF generation, invoice/payment handoff, detailed profitability allocation, sales pipeline editing and pagination beyond the current 1,000-record workspace cap are not included in this increment. Existing platform modules provide several of these backend contracts, but they are not wired into these new screens yet. AI suggestions are not introduced in this change.

## Verification

- `npm run test:practice`: contract/file validation and isolated PGlite database tests. All repository migrations are applied before behavior tests.
- Database tests cover tenant/product isolation, roles, expired grants, portal isolation, file access, immutable snapshots, optimistic conflicts, phase gates, period idempotency, recurring month-end behavior, worker restrictions and reminder suppression.
- `npm run typecheck` and `npm run build` validate the production application.
- Optional UI fixture: `npx vite --config verification/practice/ui/vite.config.ts`, then `node verification/practice/ui/smoke.mjs` with Playwright and Chromium installed. Fixture mocks are confined to the verification Vite config and are not included in the production app.
- Browser smoke/visual verification was not completed in the authoring environment because browser downloads returned invalid archives. Live provider/storage testing also remains a staging gate.
