# MoneyBridge: operator workspace and advisory connector

Source: `asaffilate01-ship-it/screen-shot-magic-526`. Keep the existing product key `fastremit`; display it as MoneyBridge. The product keeps its own operational Supabase database, users, remittance ledger/workflows, KYC/AML decisions and provider credentials. Its current schema is single-operator; consumers and recipients are not SaaS tenants. Another independent operator needs a separate deployment/database until end-to-end tenant isolation is implemented and tested. Do not infer isolation from a registry entry.

The migration registers a draft `moneybridge-uk` blueprint and optional existing AI/analytics services, and updates the display name without renaming product connections. It does not activate a tenant or services, create users/keys, change existing product status, or switch a data plane. White-label branding, identity federation, billing, event analytics, RAG/GraphRAG and multi-operator provisioning are not implemented by this registration.

## Provisioning an isolated pilot

1. Merge/deploy the MoneyBridge connector and preceding treasury snapshot migrations. Apply this Factory migration in staging. Use SaaS Factory to create the operator organisation/workspace, product link and a stable external workspace ID, e.g. `moneybridge-gb-pilot`. Use a separate data plane for a second operator.
2. Provision the product and optional `omniqora.ai` service through existing reviewed operations. Generate the scoped `oqcp_` connector credential. Source uses POST `/api/control-plane/tenant-snapshot`, schema version 4, exact `fastremit` product and internal/external IDs, active GB/GBP tenant/product, and valid entitlement dates.
3. Add a **separate** machine binding in `OMNIQORA_BRIDGES_JSON` using the existing bridge schema: product `fastremit`, exact central `tenant`, dedicated `project` and `serviceUser`, `externalTenant` equal to the MoneyBridge workspace ID, `allowedScopes` containing only that ID, `secretEnv: OQ_BRIDGE_MONEYBRIDGE_GB`, `protocol: bearer`, `contracts: [generic_draft]`, `profile: finance`, an explicit expiry and daily limit. Begin disabled; enable only after reviewing model policy and data sharing. Keys must be distinct from the control-plane credential.
4. Provision the real host/project service principal, allow the central tenant in `BUSINESS360_ENABLED_TENANTS`, configure transformation service and model policy/budget/data-sharing consent. Use the existing bridge readiness tools; a key or snapshot alone does not prove AI works.
5. Set server-only MoneyBridge variables `OMNIQORA_URL`, `OMNIQORA_TENANT_ID`, `OMNIQORA_EXTERNAL_TENANT_ID`, `OMNIQORA_CONTROL_PLANE_KEY`, `OMNIQORA_BRIDGE_KEY`, and `MONEYBRIDGE_OMNIQORA_MODE=read`. Default is off. Write mode is rejected. Never use VITE-prefixed secrets.
6. As a MoneyBridge treasury/admin user, open Platform & intelligence and request a review of a saved snapshot. Source permits only a fixed question and server-generated status counts, dates and snapshot ID; no customer names, individual amounts, bank references or payment instructions are sent. Source checks staff access and fresh entitlements before and after generation; output must require review and cite the supplied snapshot. No external action is possible through this source path.
7. Verify mismatched tenant/product/country, revocation, expired/future entitlements, missing model policy, denied roles, changed idempotency input and an actual model failure in staging. Test two isolated operators before describing this as tenant-safe live integration. Audit metadata is local; model drafts stay subject to the existing central retention policy.

Central generic drafts use `/api/integrations/gateway`. No novel gateway endpoint or fabricated model result is introduced. No automatic event stream, cross-app SSO, provider balance feed, RAG corpus or autonomous payment agent is claimed. These are later scoped integrations.
